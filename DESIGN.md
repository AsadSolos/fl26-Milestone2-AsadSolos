# M2 Technical & Design Understanding

## 1. Polymorphism and dynamic dispatch - 1.5 points

The operation of runtime polymorphism occurs in `ProcessingCore::rebuild`, which uses `impl_->chunking->chunk(doc, order)` taking a `std::unique_ptr`. The base interface is `aiws::ChunkingStrategy`; the default derived implementation is `aiws::Chunker`, and custom derived implementation includes `MarkerChunker` from `tests/student_tests.cpp` that implements the same pure virtual method `chunk(const Document&, std::size_t) const`. The default `ProcessingCore()` constructor initializes the object with `std::make_unique(...)`, which is the work of the function `rebuild`, allowing it to call `Chunker::chunk` through the vtable during runtime; the same pattern holds for the functions `search` (through `RetrievalStrategy`) and `build_context` (through `ContextStrategy`). If the method `chunk` is not declared as `virtual`, the call would be forced to call `ChunkingStrategy`'s method and would forget any injected derived implementation, thus violating M2 runtime substitution; on the other hand, declaring it pure virtual does not allow the interface to be instantiated.

## 2. Ownership and lifetime - 1.5 points

Strategy objects are created by the caller (or by `ProcessingCore()`'s default constructor) and passed as `std::unique_ptr<...>` into `ProcessingCore::Impl`, which stores them as `std::unique_ptr<ChunkingStrategy> chunking`, `std::unique_ptr<RetrievalStrategy> retrieval`, and `std::unique_ptr<ContextStrategy> context`. Ownership moves via `std::move` in the `Impl` constructor initializer list (`chunking(std::move(c)), retrieval(std::move(r)), context(std::move(x))`), and `ProcessingCore` owns `Impl` through `std::unique_ptr<Impl> impl_`, so the chain is caller -> `Impl` -> strategy. `std::unique_ptr` represents exclusive ownership: `Impl`'s destructor deletes each strategy through its base pointer exactly once, and copying is a compile error. `ProcessingCore` is move-only because `impl_` is a `unique_ptr` and duplicating it would duplicate ownership of the same strategy objects; the strategy base classes need virtual destructors because deletion happens through `ChunkingStrategy*`, `RetrievalStrategy*`, and `ContextStrategy*`, and without `virtual ~...() = default;` that would be undefined behavior and the derived destructor would not run.

## 3. Architecture, extensibility, and M1 compatibility - 1.5 points

The caller generates its strategy objects which are passed as `std::unique_ptr<...>` to the `ProcessingCore::Impl`, where they are kept as `std::unique_ptr chunking`, `std::unique_ptr retrieval`, and `std::unique_ptr context`. The ownership is performed by the `std::move` call in the constructor's initializer list of `Impl` (`chunking(std::move(c)), retrieval(std::move(r)), context(std::move(x))`), and `ProcessingCore` holds `Impl` by means of `std::unique_ptr impl_` such that the full chain is caller -> `Impl` -> strategy. In `std::unique_ptr`, exclusive ownership is implied, and thus, `Impl` destructor will delete the strategy only once and copying it leads to compile-time error, since `ProcessingCore` is move-only because `unique_ptr` can’t be copied thus leading to duplication of ownership of the same strategy objects. The reason for using virtual destructors in strategy base classes is that since deletion would be performed through `ChunkingStrategy*`, `RetrievalStrategy*`, and `ContextStrategy*`, without having the virtual destructor, the derived destructor would not be called and thus performing deletion would have undefined behavior.

## 4. Testing and defect reasoning - 1.5 points

I will address the topic of `duplicate doc id leaves previous corpus intact` in the file `tests/student_tests.cpp`, where it performs the building of a proper workspace, stores the number of chunks before rebuilding it with two documents using the same identifier `"x"`, expects the `std::invalid_argument`, and checks whether the number of chunks is equal to the value stored before. By doing so, it successfully proves the requirements mentioned in Section 8, meaning that duplicate identifiers should lead to an exception while allowing the corpus to stay unchanged because of the same system functionalities. The identified defect stems from the faulty procedure of the appending process in the loop and building the index only in the end. Thus, when an exception is raised, the chunks get overwritten while there are still indicators pointing to the old chunks, which causes an incorrect number of chunks and mixing of postings as a result of the search process. It should be noted that my implementation resolves this issue by gathering data into the local variables `next_chunks` and `next_index`, instead of implementing the operation that would take place only when the outcome is successful.
